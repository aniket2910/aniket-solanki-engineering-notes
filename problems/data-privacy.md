Problem Restatement
We want a cloud backup/sync system for a privacy-focused web app where only the user controls their data. In other words, the user’s data should never be stored in plain form on our servers or any third-party’s servers. If data is synced or backed up “to the cloud,” it must remain unreadable by anyone but the user – essentially a zero-knowledge or client-side encrypted approach. This solves the user’s concern that, for example, using Google Drive or Dropbox means they think they own the data but actually those companies could access it. We need a strategy where the cloud storage either belongs to the user (self-hosted or peer-to-peer) or is encrypted in such a way that even the storage provider “stores—but never sees—the data”.

Client-Side Encryption (Zero-Knowledge Storage)
One strong model is to encrypt everything on the user’s device before sending it anywhere. This is often called zero-knowledge storage. In this setup, the web app generates an encryption key in the browser and never sends the plaintext data or the key to the server. The server (or cloud) only ever sees ciphertext. Proton Drive’s documentation summarizes this: “your data is encrypted on your computer… before it’s transmitted to the server,” so that “no one but you can access your data.”. In practice, the client-side code uses strong cryptography (e.g. AES-256-GCM via the Web Crypto API) to encrypt data with a randomly generated key. The encrypted blob (and even file names/metadata) is then stored on the server or cloud as an opaque blob the server cannot read.

To support multiple devices, the user’s encryption key itself can be encrypted (or “wrapped”) with a passphrase and stored on the server. On each device the user enters their passphrase to unwrap the key locally. This way, the service never has the raw key. The Open Security Architecture pattern explains this carefully: “the user’s data key is encrypted (wrapped) with a key derived from their passphrase… the wrapped key is stored on the server. The user enters their passphrase on each device to unwrap the data key… [keeping] the data key itself off the server in plaintext.”. In short, only the user’s devices have the decryption key, so the user – not us or any cloud provider – truly “holds” the data.

Pros: This guarantees cloud providers or our servers see only encrypted data. Even if the cloud is breached or subpoenaed, the attacker only gets ciphertext. Proton’s overview notes that this “prevents any data breach from affecting you on the server side” and ensures privacy from companies that might scan or exploit your files.

Cons: The user is fully responsible for the encryption key. If they lose their key (e.g. clear browser storage or lose a device), the data is irrecoverable. In fact, “key loss = data loss (by design)”. We must therefore build in clear key backup and recovery options. Also, because the provider can’t read the data, features like server-side search or analytics become much harder. All processing happens on the client side.

Decentralized and Self-Hosted Storage
Another approach is to avoid any third-party cloud by using peer-to-peer or self-hosted solutions. For example, Syncthing is an open-source P2P file sync tool. It makes each device sync directly with other devices (or with the user’s own servers) without a central server. On Syncthing, “none of your data is ever stored anywhere else other than on your computers. There is no central server”. All connections are encrypted with TLS, and each device must be explicitly authorized. In effect, the “cloud” is just the network of the user’s devices. This fully preserves privacy because the data literally never touches an untrusted third party. A similar concept is a personal cloud server (e.g. a self-hosted Nextcloud instance). The user would own that server, so again they keep control.

Decentralized storage networks like IPFS or Sia/Storj can also be used. These break files into encrypted shards distributed across many nodes. For instance, Sia’s model “splits each file into tiny encrypted shards… [and then] distributes them across our decentralized network,” and promises it “stores—but never sees—your data”. IPFS is a peer-to-peer content-addressable storage system; users can run their own nodes or private IPFS networks so they retain control. As one writer notes, with IPFS “users can maintain control over their data and maintain increased security and privacy”. The trade-off with these systems is complexity: users need to run (or pay for) nodes, pin data to keep it alive, or deal with cryptocurrency payments, etc. But they achieve the goal of a user-controlled storage layer outside traditional cloud.

Encrypting Data on Third-Party Clouds
A practical middle-ground is to let users continue using familiar cloud accounts (Google Drive, Dropbox, etc.) but only after encrypting data locally. For example, tools like Cryptomator allow a user to choose a folder in their cloud drive as a “vault.” Cryptomator encrypts every file (and even filenames) on the user’s device before syncing to the cloud. Its slogan is that “the key to your data is in your hands,” meaning only the user’s password can decrypt those files. With this approach, the user technically uses Google’s or Dropbox’s storage, but those services never see the plaintext. Similarly, our web app could let the user authorize their own Google Drive (or other storage) account via OAuth, then store the user’s data in an encrypted form there. The server would only act as a broker for encrypted blobs. Columbia University’s ESP project did something like this for photos: it encrypts photos on-device and uploads them to Google Photos, so that “even if your account is hacked, attackers can’t get your photos because they are encrypted.”.

The benefit of this method is convenience: users can use accounts they trust for convenience (with built-in quotas), while we still provide end-to-end encryption. The downside is that users must still trust that the encryption is implemented correctly and their keys are secure. And again, syncing across devices requires safely sharing the encryption key (as Columbia’s researchers solved by device verification).

Implementation Patterns and Trade-Offs
Putting these ideas into practice means choosing a balance of usability, security, and trust. Key considerations include:

Key Management: If data is encrypted end-to-end, the user’s key is critical. We must provide simple key backup and recovery (for example, exporting a key file or using a passphrase-derived key). Warn users that losing the key means losing data.
Multi-Device Sync: For multiple devices, use a key-wrapping scheme or device pairing. Columbia’s ESP encrypted cloud solution, for instance, has users verify new devices against existing ones so that encrypted keys can be securely shared.
Performance and Features: Encrypting on the client means more CPU work on the user’s device and larger data to transfer (encryption adds overhead). Server-side features like full-text search or thumbnails become tricky. (The Columbia team solved image thumbnails by uploading encrypted thumbnails, but not all apps can easily do that.)
Trust Model: Even if using user’s own Google Drive, emphasize the difference: unlike typical cloud storage, here the user holds the decryption key. As Proton notes, many popular providers “do not use end-to-end encryption or zero-access encryption,” so without our measures we can’t promise privacy. By contrast, systems like Sia or Syncthing offer cryptographic guarantees that only the user (or explicitly authorized parties) can see the data.
Backup Strategy: Since no plaintext is on our server, we must rely entirely on the user’s chosen backups. This might mean integrating with external backup solutions or instructing users to export their encrypted data regularly.
Recommended Approaches
In practice, a common recipe is: encrypt everything on the client with a user-generated key, then sync encrypted data to either user-controlled storage or a third-party service. For example:

Use Web Crypto API to encrypt the user’s database or files on the fly.
Let the user choose a cloud provider (or self-hosted endpoint) to store the encrypted blobs.
Ensure the user’s key is never sent to any server in plaintext.
Offer optional device pairing for easy multi-device use (e.g. scanning a QR code from one device to another to transfer a wrapped key).
Clearly explain to users that the data is end-to-end encrypted: “only you have the keys”, giving them confidence their data is safe and truly “with them” in the cloud.
Each approach has trade-offs in usability vs. security, but all accomplish the goal of making the user the sole controller of their data. These privacy-by-design patterns have been implemented in various forms (encrypted backups, zero-knowledge cloud drives, decentralized storage). By following them, we can build a backup/sync feature where the user – not the app or any provider – holds the actual data keys.
